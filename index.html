시연

문제 정의

분실물의 접수·인식·보관·반환 과정이 사람 손을 많이 타고 대기 시간이 길다는 점에 착안해, 사람 개입을 최소화한 멀티로봇 협업 관리 시스템을 구현했습니다. 2인 팀 프로젝트로, 컴퓨터 비전 · 매칭 알고리즘 · TurtleBot 자율주행을 담당했습니다.

핵심 기능

  • YOLOv8 기반 분실물 카테고리 분류 및 OpenCV 배경 분리·색상 추출
  • 픽셀 좌표 → Dobot 좌표 homography 변환으로 정밀 피킹 좌표 산출
  • LLM 기반 분실물 ↔ 신고 유사도 매칭 (시간 · 장소 · 설명)
  • 임계값 2단계 분기 — 자동 매칭 / 관리자 검토 / 계속 탐색
  • slam_toolbox 기반 사전 맵 생성 및 AMCL 위치 추정
  • Nav2 기반 창고 ↔ 반환 창구 자율주행

시스템 구성

비전 시스템 MY PART

  • 작업대 위 분실물 촬영 후 YOLOv8 탐지 → 색상 추출 → LLM 자연어 설명 생성
  • 카메라 캘리브레이션과 homography로 Dobot 픽업 좌표 변환

매칭 시스템 MY PART

  • 같은 카테고리 · 최근 30일 이내 후보로 필터링 후 유사도 점수 계산
  • 점수 기준으로 자동 매칭 / 검토 / 탐색 상태 분기 및 인증코드 · 메일 트리거
  • 매칭 결과를 DB에 적재하고 REST API로 전달하는 구간까지 직접 구현

TurtleBot 자율주행 MY PART

  • named pose(Dobot 근처, 반환 창구, 대기) 기반 목표 이동
  • Nav2 navigate_to_pose 액션으로 경로 계획 및 장애물 회피

Dobot · 백엔드 · 키오스크 TEAM

  • ROS 2 / rosbridge / REST로 비전 · 매칭 · 주행 모듈과 연동

설계 포인트

픽셀 좌표를 로봇 좌표로 옮기기

  • 체커보드 캘리브레이션으로 렌즈 왜곡과 카메라 파라미터를 먼저 보정
  • 보정된 영상의 바운딩 박스 중심을 homography 변환으로 Dobot 작업 평면 좌표에 매핑

매칭 임계값 2단계 분기

  • 임계값 하나로는 애매한 후보에서 오매칭과 누락이 동시에 발생
  • 자동 매칭 임계값과 검토 임계값을 분리해, 사이 구간은 관리자 검토로 넘기는 구조
  • 확신이 없을 때 자동 처리하지 않는 쪽을 기본값으로 선택

사전 맵 기반 주행

  • slam_toolbox로 매장 맵을 미리 만들고, 주행 시에는 AMCL로 위치만 추정
  • 목적지를 named pose로 등록해 상위 로직은 좌표 대신 이름으로 명령

용도별 LLM 모델 선정

  • 매칭은 신고 1건당 같은 카테고리 물건 수만큼 반복 호출되고, 묘사는 물건 등록 시 1회만 호출됩니다
  • 호출 빈도가 다르므로 하나의 기준으로 고르지 않고, 매칭은 정확도·비용, 묘사는 정밀도를 우선 기준으로 분리
  • 텍스트 매칭 — 후보 5종을 1:1 매칭과 8개 케이스 풀 매칭으로 돌려 정답률·응답속도·크레딧 측정 → gpt-4o-mini 2C
    • 두 테스트 모두 100% 정답, 평균 응답 1.94s
    • 정답률이 같은 gpt-4.1-mini 대비 크레딧 절반
    • gpt-5-nano는 정답률 75%에 응답도 10초대라 제외
  • 이미지 묘사 — 세부 특징이 많은 같은 사진을 5종에 동일하게 넣고 식별 정확도 비교 → gemini-3.5-flash 18C
    • 이름·카드번호까지 읽어내 후보 중 가장 정밀
    • gemini-2.5-flash와 성능은 동등하면서 12C 저렴

문제 해결

카메라가 인식한 픽셀 좌표와 Dobot의 실제 좌표가 맞지 않아 피킹이 빗나갔습니다.

체커보드 캘리브레이션으로 카메라 파라미터를 보정하고, homography 변환으로 픽셀 중심을 Dobot 좌표로 매핑해 피킹 정확도를 확보했습니다.

매칭 임계값을 하나만 두면 애매한 후보에서 오매칭 또는 누락이 발생했습니다.

자동 매칭 임계값과 검토 임계값을 분리해, 애매한 구간은 관리자 검토로 넘기는 2단계 구조로 오매칭을 줄였습니다.

설계 포인트

알코올 센서 ADC 처리

  • 알코올 농도 → 센서 저항 변화 → 아날로그 전압 변화의 경로로 감지
  • ATmega128의 10비트 ADC로 0~1023 값으로 변환  ADC값 = (입력전압 / 기준전압 5V) × 1023
  • measure_alcohol()에서 값을 읽고 100으로 나눠 정규화한 뒤 패킷 상위 4비트에 패킹
  • 테스트는 실제 음주 대신 고농도 에탄올(손소독제)로 센서 반응을 확인

UART 패킷 설계 — 1바이트 패킹

비트내용판정
상위 4비트알코올 값fromhelmet >= 0x40 → 음주
하위 1비트헬멧 착용 여부fromhelmet & 0x01 → 착용
  • 1초 주기 타이머 인터럽트로 전송해 통신 횟수를 고정

인터럽트 설계

  • TIMER1_OVF — 1초 주기로 안전 상태 감시 + LCD 갱신 + UART 송신
  • SIG_UART1_RECV — 수신 즉시 fromhelmet 갱신만 수행 (ISR 최소화)
  • INT0 — 버튼. 라이징/폴링 엣지를 전환해 딜레이 없이 모터 ON/OFF
  • ISR을 최소화한 이유 — ISR이 길어지면 메인 루프가 블로킹되고, 타이머 주기가 어긋나며, 그 사이 들어온 인터럽트를 놓칠 수 있습니다.

문제 해결

터치 센서(TTP223)가 머리카락 때문에 헬멧 착용을 제대로 감지하지 못했습니다.

손(털 없음) → 이마(털 없음) → 앞머리 조금 → 앞머리로 완전히 덮음 순으로 조건을 바꿔가며 출력 로그(0/1)를 확인했고, 머리카락이 많을수록 0이 늘어나는 것을 확인했습니다.

원인은 TTP223이 임계값을 조절할 수 없는 디지털 출력이라는 구조적 제약이었고, 소프트웨어로는 해결할 수 없는 문제였습니다.

헬멧은 머리에 밀착 착용하는 것이 올바르다는 점을 반영해, 착용하는 동안 항상 눌린 상태가 유지되는 스위치 센서로 교체했습니다. 단위 테스트(손)에서는 통과했지만 통합 테스트(실제 헬멧 + 사람)에서 드러난 문제였습니다.

헬멧부와 킥보드부 간 데이터 전송 시 여러 값을 개별 전송하면 지연이 발생했습니다.

알코올 수치와 헬멧 착용 여부를 1바이트로 패킹하고, 1초 주기 타이머 인터럽트로 전송해 통신 횟수와 지연을 줄였습니다.

설계 포인트

인식과 제어의 노드 분리

  • 분리 전 — YOLOv5 추론은 Jetson Nano GPU에서도 50ms를 넘길 수 있습니다. 이 추론이 제어 루프를 블로킹해 20Hz 주기가 불안정해졌고, PX4 OFFBOARD 모드가 요구하는 2Hz 이상의 setpoint 스트림이 끊길 위험이 있었습니다.
  • 분리 후 — 제어 노드가 인식 속도와 무관하게 20Hz(50ms)를 고정 유지합니다. 인식이 늦어도 마지막 유효 명령을 계속 전송해 스트림이 끊기지 않습니다.

3축 독립 제어 cent()

축판단 기준반환
X 전진·후진바운딩 박스 면적 vs 기준 면적 (±768)+1 전진 / −1 후진
Y Yaw 좌우박스 중심 x vs 화면 중심 (±32px)+1 오른쪽 / −1 왼쪽
Z 상승·하강박스 중심 y vs 화면 중심 (±24px)+1 위 / −1 아래
  • 범위 안이면 0을 반환하는 dead zone을 두어 미세 오차를 무시
  • 반환값이 −1 / 0 / +1 부호뿐이므로 PID가 아니라 방향 신호

누적 카운터와 Fail-Safe

  • 방향 신호를 cnt에 누적해 임계값 15를 넘을 때만 고정 속도 0.2로 명령
  • 방향이 급격히 반전되면 cnt를 리셋해 오인식으로 인한 급기동을 방지
  • cnt_det — 탐지 0개면 +1, 1개 이상이면 50으로 리셋(호버링)
  • cnt_det > 150, 약 100프레임 연속 미탐지면 det_msg = -1로 자동 착륙

문제 해결

YOLOv5 추론이 제어 루프를 붙잡아 20Hz 주기가 흔들렸고, OFFBOARD 스트림이 끊길 위험이 있었습니다.

인식과 제어를 별도 ROS 노드로 분리해, 제어 노드가 인식 속도와 무관하게 20Hz를 고정 유지하도록 만들었습니다.

실내라 GPS 위성 신호가 차단되어 드론의 절대 위치를 알 수 없었습니다.

대안으로 RealSense depth 스트림을 활성화해 위치 추정을 검토했습니다.

하지만 이 시스템에 필요한 것은 "내가 (x, y, z)에 있다"는 절대 위치가 아니라 "타겟이 화면 중심에서 왼쪽 32px에 있다"는 상대 위치뿐이라는 점을 확인했고, 바운딩 박스만으로 충분해 depth와 SLAM은 쓰지 않았습니다.

드론 자체의 odometry는 PX4가 내부에서 IMU(가속도계·자이로)로 추정하며, 저는 그 위에서 MAVROS로 속도 명령을 전달하는 제어 레이어를 담당했습니다.

제어 방식을 두고 팀 내에서 위치 제어와 속도 제어 의견이 갈렸습니다.

위치 제어는 목표까지의 거리가 멀수록 입력이 커져 관성으로 오버슈트가 생깁니다. 속도 제한을 걸 수는 있지만, 타겟이 매 순간 바뀌는 팔로잉에는 매 순간 속도를 조절하는 방식이 더 자연스럽습니다.

두 방식을 모두 구현해 실제 안정성을 비교한 뒤 속도 제어를 채택했습니다.

드론의 불안정한 비행으로 통신까지 불안정해지는 문제가 있었습니다.

하드웨어를 물리적으로 더 단단하게 결합해 진동을 줄이고 통신 안정성을 높였습니다.

문제 해결

초기 표정 인식 모델의 정확도가 낮았습니다.

기존 데이터셋이 서양인 및 흑백 위주라는 점을 먼저 분석했습니다.

동양인 비중이 높은 데이터셋을 추가하고, angry / neutral 클래스 수 불균형을 확인했습니다.

가중치 조정과 data augmentation(cut-out, crop, noise 등)을 적용해 모든 클래스에서 85% 이상의 정확도를 달성했습니다.

사용자 식별에 ResNet 계열 모델을 사용하면 재학습 시간이 길고 데이터도 충분하지 않았습니다.

K-NN을 활용해 적은 데이터로도 빠르게 사용자 데이터를 구축하는 방식으로 전환했습니다.
